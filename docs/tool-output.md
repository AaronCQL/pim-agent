# Tool Output

A tool returns `{ content, details }`. The two channels have different audiences.

- **`content` → the model.** Pi tags anything `execute` throws as `isError: true` and providers map that to native error semantics. A prose "this failed" string does not — the model reads it as success. **Throw for every error and edge case** (not found, empty, out of range, permission denied); never return an English error string in `content`.
- **`details` → renderers only.** Providers do not serialize it. Pagination metadata, byte counts, paths, diff objects (`ToolDiff`), exit codes go here so the TUI can show affordances without the text leaking to the model. See `bash`'s `detailsOf()` (`packages/core/src/extensions/bash/format.ts`) and the diff carried by `edit`/`write`.
- **Partial success** must live in `content`, fenced in square brackets — e.g. `[read tool: showing lines 1-50 of 200; call read again with start=51 to continue.]`. Emit body and footer as separate `content` blocks so renderers can detect the pattern, and mirror the structured fields into `details` (`read`, `glob`, `grep`, `web_fetch`). When the full output is too large to keep inline, spill it with `SpillCache` (owns `~/.pim/cache`, 0600 writes, TTL sweep) and point the footer at the saved path with a resume line from `Lines.continuationLine` instead of asking the model to re-run.
- **Errors must be actionable**: include the error code, name what failed, and suggest the next call ("use glob to locate the file"). Canonical: `read.ts`, `edit.ts`, `bash/run.ts`. File/dir stats go through `FsErrors.statOrThrow`.
- **Argument validation is `Tools.wrap`'s job** — `execute` only sees args that passed the schema. Throw for *semantic* errors, and for type errors only when the schema cannot express the constraint.
